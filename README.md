# Cash Flow

Проект рассчитывает будущие денежные потоки по сделкам из CSV-файла и приводит их к стоимости на дату оценки.

Результат содержит отдельно:

- погашение основного долга (`principal_cf`);
- выплату процентов (`interest_cf`);
- остаток долга до и после платежа;
- коэффициент дисконтирования;
- дисконтированные principal и interest;
- полную приведённую стоимость платежа (`present_value`).

## Общая последовательность расчёта

Для каждой сделки выполняются следующие шаги:

1. Входная строка преобразуется в `Deal`, `RateSpec` и `ScheduleRule`.
2. Строится расписание погашения principal.
3. Платежи principal группируются по датам.
4. Определяются даты выплат основной и дополнительной процентных ставок.
5. Даты principal, процентов и maturity объединяются в единый список событий.
6. Между соседними событиями начисляются проценты на текущий остаток.
7. В даты процентных выплат накопленные проценты превращаются в `interest_cf`.
8. После начисления процентов выполняется погашение principal и изменяется баланс.
9. Каждый полученный cash flow дисконтируется по бескупонной G-кривой ОФЗ.
10. Результат записывается в CSV.

## 1. Парсинг сделки

Основные входные параметры:

- `report_dttm` — дата оценки;
- `maturity_dttm` — дата окончательного погашения;
- `current_principal_amt` — остаток principal на дату оценки;
- `discriminator` — способ погашения principal;
- `rate_type_cd` — `FIXED` или `FLOAT`;
- `interest_rate` — полная ставка для `FIXED` или спред для `FLOAT`;
- `base_indicator` — код плавающего индикатора, например `CBKEY1M`;
- `day_convention_cd` — правило определения доли года;
- правила платежей, repricing и явные расписания;
- cap, floor, коэффициент индикатора и lag;
- дополнительная ставка `sub_rate`.

`report_dttm` и `deal_report_dttm` должны совпадать. Идентификаторы сделок должны быть уникальными.

## 2. Расписание погашения principal

Явное расписание имеет приоритет над значением `discriminator`.

### Явное расписание

Если заполнено `principal_payment`, алгоритм:

1. отбрасывает платежи на дату оценки и раньше;
2. запрещает платежи после maturity;
3. объединяет суммы с одинаковой датой;
4. не позволяет погасить больше текущего остатка;
5. переносит непогашенный остаток на maturity.

Если последний явный платёж уже находится на maturity, остаток прибавляется к нему. Иначе на maturity создаётся отдельный платёж.

### SIMPLE

Весь principal погашается на maturity:

```text
maturity_date -> outstanding_principal
```

### RGM

Principal делится на приблизительно равные части по всем датам погашения:

```text
regular_principal = outstanding_principal / number_of_payments
```

Это аналог дифференцированной схемы: principal-часть примерно постоянна, а проценты зависят от остатка и длительности конкретного периода. Общий платёж не является постоянным и в целом снижается вместе с балансом. Последний principal корректируется на остаток округления.

### ANN

При аннуитетной схеме примерно постоянным является общий платёж, а не величина погашения principal.

Для каждого периода сначала определяется периодическая ставка:

```text
period_rate = annual_rate * year_fraction
```

Для переменных по длине периодов используются коэффициенты:

```text
DF_i = 1 / ((1 + r_1) * ... * (1 + r_i))
```

Аннуитетный платёж:

```text
payment = principal / sum(DF_i)
```

Разбиение платежа:

```text
interest_i = balance_before_i * period_rate_i
principal_i = payment - interest_i
```

В последний период погашается весь оставшийся principal.

## 3. Генерация дат

Поддерживаются правила:

- `1M`, `2M` и другие месячные интервалы;
- `45D`, `153D` и другие интервалы в календарных днях;
- `ENDDATE` — единственная дата на maturity.

`day_num` определяет день месяца:

- `None` — день из `start_date`;
- `1..31` — конкретный день;
- `-1` — последний календарный день месяца.

Если требуемого дня в месяце нет, используется последний день этого месяца. Maturity всегда добавляется в расписание.

Корректировка на выходные и праздничные дни не выполняется.

## 4. Даты выплаты процентов

Приоритет определения дат:

1. явное расписание `interest_payment`;
2. `payment_rule` процентной ставки;
3. даты платежей principal, если отдельное процентное расписание отсутствует.

Maturity всегда считается датой выплаты оставшихся накопленных процентов.

Для `sub_rate` строится отдельное расписание. Дополнительная ставка может начинать начисляться позже `report_date`: в этом случае используется более поздняя из `report_date` и `sub_payment_rule_start_dttm`.

## 5. События и движение баланса

В единый отсортированный набор объединяются:

- даты погашения principal;
- даты выплаты main interest;
- даты выплаты sub interest;
- maturity.

Дата repricing используется  для разделения процентного периода на сегменты с разными ставками.

Для каждого события:

1. начислить main interest на `balance_before`;
2. начислить sub interest, если дополнительная ставка уже действует;
3. выплатить накопленные проценты, если событие является датой их выплаты;
4. получить `principal_cf` для текущей даты;
5. рассчитать новый остаток:

```text
balance_after = balance_before - principal_cf
```

* principal считается выплаченным в конце процентного периода: проценты до даты платежа начисляются на старый остаток, а со следующего сегмента — на новый.

* Если на событии principal меняется, но проценты не выплачиваются, начисленная сумма сохраняется в накопителе до следующей процентной даты.

## 6. Расчёт ставки

### FIXED

Для фиксированной сделки используется полная договорная ставка:

```text
annual_rate = interest_rate
```

Ключевая ставка в расчёте fixed interest не участвует. Если для сделки заданы cap или floor, они применяются и к фиксированной ставке.

### FLOAT

Для плавающей сделки `interest_rate` трактуется как спред:

```text
annual_rate = interest_rate + coefficient * indicator_rate
```

Если `coefficient` отсутствует, используется `1`.

После расчёта применяются ограничения:

```text
annual_rate = max(annual_rate, floor)
annual_rate = min(annual_rate, cap)
```

Если задано явное значение из `rate_schedule` или `fixed_rate_schedule`, оно имеет приоритет для соответствующего периода.

## 7. CBKEY1M и repricing

История `CBKEY1M` загружается из `data/cbkey1m.csv`. Значения в CSV хранятся в процентах и при чтении переводятся в доли:

```text
8.0 -> 0.08
```

Для определения ставки:

1. находится последняя дата repricing, не превышающая начало сегмента;
2. к ней применяется `indicator_lag_cd`, если он задан;
3. для исторической даты выбирается значение CBKEY1M, действовавшее в этот день;
4. для будущей даты используется последнее значение, известное на `report_date`.

Дата наблюдения ограничивается датой оценки:

```text
observation_date = min(fixing_date, report_date)
```

Если внутри процентного периода находится repricing, период разбивается:

```text
01.09-15.09 -> ставка до repricing
15.09-01.10 -> ставка после repricing
```

Полная ставка периода равна сумме ставок сегментов с учётом их долей года.

## 8. Day count

Поддерживаются:

### ACT/365

```text
year_fraction = actual_days / 365
```

### ACT/ACT и ACT/ACT ISDA

Период разбивается по календарным годам. Для каждого сегмента используется фактическое количество дней в соответствующем году:

```text
year_fraction = days_in_ordinary_year / 365
              + days_in_leap_year / 366
```

`ACT/ACT` трактуется как `ACT/ACT ISDA`.

## 9. Накопленные и дополнительные проценты

`accrued_interest` добавляется к основному процентному накопителю на `report_date` и выплачивается вместе со следующей main interest выплатой.

Main и sub interest начисляются независимо. У них могут различаться:

- даты выплат;
- repricing rules;
- lag;
- спред;
- коэффициент индикатора;
- cap и floor.

Если main и sub interest выплачиваются в одну дату, они объединяются в один `interest_cf`.

`interest_period_start` и `interest_period_end` являются описательными полями. Когда в одну дату объединяются main и sub interest с разными началами периодов, в `interest_period_start` записывается самая ранняя дата. Если в событии нет процентной выплаты, обе границы равны `cashflow_date`.

## 10. Дисконтирование

Ключевая ставка и G-кривая выполняют разные функции:

```text
CBKEY1M  -> определяет размер процентов по FLOAT-сделке
G-кривая -> определяет текущую стоимость будущего cash flow
```

Дисконтируются principal и interest как фиксированных, так и плавающих сделок.

Для каждого cash flow срок определяется по `ACT/365`:

```text
term = (cashflow_date - report_date).days / 365
```

Значение бескупонной ставки `z(term)` получается линейной интерполяцией между опубликованными узлами G-кривой ОФЗ

Поскольку кривая задана для непрерывно начисляемой ставки:

```text
discount_factor = exp(-z(term) * term)
```

Текущая стоимость компонентов:

```text
discounted_principal_cf = principal_cf * discount_factor
discounted_interest_cf = interest_cf * discount_factor
present_value = discounted_principal_cf + discounted_interest_cf
```


## 11. Округление

Денежные значения округляются до копеек через `ROUND_HALF_UP`.

Остаток principal после округлений переносится в последний платёж, поэтому конечный баланс сделки равен нулю.

Дисконтированные principal и interest сначала округляются отдельно, затем складываются:

```text
present_value = round(principal_cf * DF) + round(interest_cf * DF)
```

Это может отличаться на одну копейку от округления общей суммы одним действием.

## 12. Формат результата

| Колонка | Значение |
| --- | --- |
| `deal_id` | идентификатор сделки |
| `cashflow_date` | дата денежного потока |
| `currency` | валюта сделки |
| `interest_period_start` | начало оплачиваемого процентного периода |
| `interest_period_end` | конец оплачиваемого процентного периода |
| `principal_cf` | погашение principal |
| `interest_cf` | выплата процентов |
| `balance_before` | остаток до погашения principal |
| `balance_after` | остаток после погашения principal |
| `discount_factor` | коэффициент дисконтирования |
| `discounted_principal_cf` | приведённая стоимость principal |
| `discounted_interest_cf` | приведённая стоимость процентов |
| `present_value` | полная приведённая стоимость строки |

## Ограничения текущей реализации

- Между опубликованными узлами используется линейная интерполяция, а не полное восстановление параметрической функции Московской биржи
- Для сроков короче первого и длиннее последнего узла используется ближайшая граничная ставка
- Перенос платежей с выходных и праздников не выполняется
- Не поддерживаются валютная конвертация и отдельные кривые для разных валют
- Текущая реализация ориентирована на сценарии, присутствующие в исходном демонстрационном файле
